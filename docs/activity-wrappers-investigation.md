# Activity Wrappers Investigation — ONScripter, Ren'Py, Godot

> **Date:** 2026-06-01
> **Purpose:** Investigate what's needed to turn the bundled .so files into working game engines in Runestone

---

## Current Status

All three have their native .so files bundled in `jniLibs/arm64-v8a/` but lack the Java Activity wrapper that bridges the native engine to Android's lifecycle. Currently they all show "Coming Soon" dialogs via `UnavailableEngine.kt`.

---

## 1. ONScripter (NScripter Visual Novels)

**Bundled .so files:**
- `libonscripter.so` (2.3 MB) — the ONScripter game engine
- `libsdl.so` (592 KB) — SDL 1.2 for rendering/input

**Source repo:** `matthewn4444/onscripter-engine-android` (GPLv2+)

### Architecture

The ONScripter Android wrapper has **two layers:**

```
┌──────────────────────────────┐
│  ONScripter (Activity)       │ ← App layer: handles UI, settings, gestures
│  - com.onscripter.plus       │
├──────────────────────────────┤
│  ONScripterGame (Fragment)   │ ← Game host: manages ONScripterView layout
│  - com.onscripter.plus       │
├──────────────────────────────┤
│  ONScripterView (GLSurface)  │ ← JNI bridge: loads libonscripter + libsdl
│  - com.onscripter            │
├──────────────────────────────┤
│  DemoGLSurfaceView           │ ← SDL GL rendering surface
│  GLSurfaceView_SDL           │
├──────────────────────────────┤
│  libonscripter.so            │ ← Native engine (bundled)
│  libsdl.so                   │ ← SDL 1.2 (bundled)
└──────────────────────────────┘
```

### JNI Interface (from ONScripterView.java)

The key Java class `com.onscripter.ONScripterView` exposes:

```java
// Construct with builder containing game path, font, save path
new ONScripterView(Builder builder)

// Native methods called via JNI:
native void nativeSetSentenceFontScale(double scale);
native void nativeLoadSaveFile(int number);
native int nativeGetDialogFontSize();

// Callbacks from native code (static):
static void receiveMessageFromNDK(int mode, boolean flag);

// Lifecycle that must be forwarded:
onPause(), onResume(), onTouchEvent(), exitApp()
```

### What's Needed

**Option A (recommended):** Use the engine-android repo as a submodule.

Add `matthewn4444/onscripter-engine-android` as a git submodule under `native/onscripter-engine-android/`. This provides:
- `com.onscripter.ONScripterView.java` — the JNI bridge view
- `com.onscripter.DemoGLSurfaceView.java` — GL rendering surface
- `com.onscripter.GLSurfaceView_SDL.java` — SDL surface wrapper
- `com.onscripter.Audio.java` — audio thread
- C++ source for all native libs (build with NDK or use our pre-built .so)

Add a minimal Activity that creates an ONScripterView with the game path:

```kotlin
class OnscripterActivity : Activity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        val gamePath = intent.getStringExtra("game_path") ?: return finish()
        val gameDir = File(gamePath)
        
        val builder = ONScripterView.Builder(this)
            .setGameDirectory(gameDir)
            .setSaveDirectory(File(gameDir, "saves"))
            .setFontPath(null) // auto-detect
        val view = ONScripterView(builder)
        setContentView(view)
        
        view.setONScripterEventListener(object : ONScripterEventListener { ... })
    }
    override fun onPause() { view.onPause(); super.onPause() }
    override fun onResume() { view.onResume(); super.onResume() }
}
```

**Option B (minimal):** Write a barebones SDL Activity that loads `libonscripter.so` directly via `System.loadLibrary("onscripter")` and passes argv. More complex — would need to replicate GLSurfaceView_SDL.

### Complexity: **Medium**
- ~3 Java files needed from the engine-android submodule
- OR ~1 Activity file with a thin wrapper around the JNI bridge
- The hard part is getting the cmake/NDK build to compile for our specific .so versions
- Our pre-built .so may not match the Java JNI bridge API exactly

## 2. Ren'Py (Visual Novel Engine)

**Bundled .so file:**
- `librenpython.so` (55 MB) — Python 3.x + SDL2 + Ren'Py runtime, all compiled together

**Source:** `renpy/renpy-build` (MIT license)

### Architecture

Ren'Py's Android build uses **python-for-android** to compile a monolithic `.so` that contains:

```
librenpython.so
├── Python 3.x interpreter
├── SDL2 (rendering, input, audio)
├── Pygame/SDL2 (surface management)
├── Ren'Py engine libraries
└── Game script loader
```

The Android bootstrap (`PythonActivity`) is generated by RAPT (Ren'Py Android Packaging Tool).

### Key Challenge: How Ren'Py Games Work on Android

Ren'Py games are **compiled into the APK** during the build process. The standard workflow is:

1. Developer runs `renpy android build` on a project
2. RAPT wraps the game into an APK with:
   - `librenpython.so` (the Python+SDL+Ren'Py monolith)
   - `PythonActivity.java` (the bootstrap)
   - Game assets inside `assets/` or as a separate `.rpa` archive
3. `PythonActivity.onCreate()` extracts game assets from APK, sets up `PYTHONPATH`, `ANDROID_PUBLIC`, `ANDROID_PRIVATE` environment variables
4. Loads `libpython` and starts `renpy.main()`

**Generic player approach doesn't exist.** There is no "Ren'Py game launcher" that can load arbitrary Ren'Py games from a folder. Every Ren'Py Android game is a custom APK.

### What's Needed

**The hard way (not recommended):** Build a generic Ren'Py bootstrap that:
1. Copies game files from the import directory to a temp location
2. Sets up Android environment (PYTHONHOME, ANDROID_PRIVATE, etc.)
3. Loads `librenpython.so` with Ren'Py pointing at the game dir
4. Handles Python's file system access on Android (SAF compatibility)

This is difficult because:
- Ren'Py expects `renpy.py` and other files in a specific location
- The Python runtime needs `PYTHONHOME` set to a dir with stdlib files
- Game assets need to be accessible as regular files (not content URIs)
- Ren'Py's save system writes .save files to specific locations

**The practical way:** Follow JoiPlay's approach — create a **separate Ren'Py plugin APK** for each game (or for major games), rather than a generic launcher.

OR: Use the Ren'Py SDK to build the game into a standalone APK, then Runestone just installs and launches that APK.

### Complexity: **High**
- No existing generic Ren'Py Android launcher
- Ren'Py's Android integration requires python-for-android's full build pipeline
- File system access is tricky on modern Android (scoped storage)
- The `librenpython.so` alone is useless without Ren'Py's asset structure

## 3. Godot Engine

**Bundled .so file:**
- `libgodot_android.so` (142 MB) — Godot 4.6.3 engine runtime

**Maven coordinate:**
- Group: `org.godotengine`, Artifact: `godot`, Version: `4.6.3.stable`
- Hosted on Maven Central: `https://repo1.maven.org/maven2/org/godotengine/godot/`

### Architecture

The Godot Android library provides a complete Java->C++ bridge for embedding:

```
┌──────────────────────────────────┐
│  Runestone App                   │
│  ┌───────────────────────────┐   │
│  │ GodotActivity (extend me) │   │ ← Provided by org.godotengine:godot AAR
│  ├───────────────────────────┤   │
│  │ Godot Java API            │   │ ← Lifecycle, rendering, input
│  ├───────────────────────────┤   │
│  │ libgodot_android.so       │   │ ← Godot engine runtime (we bundle it)
│  └───────────────────────────┘   │
└──────────────────────────────────┘
```

### How It Works

1. Add `implementation("org.godotengine:godot:4.6.3.stable")` to build.gradle.kts
2. Create a class that extends `org.godotengine.android.GodotActivity`
3. Override `getGamePath()` to return the .pck file path

```kotlin
class RunestoneGodotActivity : GodotActivity() {
    override fun getGamePath(): String {
        return intent.getStringExtra("game_path") ?: super.getGamePath()
    }
}
```

4. Register the Activity in AndroidManifest.xml
5. Pass the game path via Intent extras from Runestone's GameActivity

### Key Issue: Lib Duplication

The `org.godotengine:godot` AAR **also contains `libgodot_android.so`**. If we add the Maven dependency AND keep our bundled .so in jniLibs, we'll have duplicates.

**Options:**
- **Remove our bundled .so** and let Gradle extract it from the AAR (cleaner, but adds build dependency on Maven)
- **Keep our .so** and use a `compileOnly` dependency on Godot AAR for Java classes only, providing our own .so at runtime (trickier)
- **Download the AAR** and extract just the Java classes jar, bundle it locally

**Plus: Godot games run differently.** Godot games ship as single `.pck` files (Godot's packed data format) or as standalone APKs. A `.pck` file is the Godot equivalent of an .exe.

Most fangames are NOT distributed as `.pck` files — they're distributed as:
- Windows/macOS exports (.exe + data folder)
- Standalone APKs (already signed with their own package name)
- HTML5 exports (playable in browser)

You'd need developers to specifically export a `.pck` + Godot APK template.

### Complexity: **Low-Medium** (technically)
- The AAR exists, the API is well-documented
- The Activity wrapper is ~20 lines of Kotlin
- **BUT:** Most Godot fangames don't ship as .pck files
- The .so is 142MB — 63% of your APK size — for a feature that may have zero playable games
- Need to verify .pck file detection and Godot version compatibility

## Summary & Recommendations

| Engine | Bundled .so | Java Needed | Difficulty | Recommendation |
|--------|-------------|-------------|------------|----------------|
| **ONScripter** | 2.3 MB | 3-5 Java files from engine-android submodule | **Medium** | Add as submodule + minimal Activity wrapper. Most achievable of the three. |
| **Ren'Py** | 55 MB | Full PythonActivity bootstrap (complex) | **High** | Don't do generic launcher. Use Ren'Py SDK to build per-game APKs instead. |
| **Godot** | 142 MB (63% of APK!) | ~20 lines extending GodotActivity + Maven dep | **Low** (tech) / **High** (game availability) | Low dev effort but games aren't distributed as .pck. Better to ask: would anyone use this? |

### Recommended Order

1. **ONScripter first** — small .so, well-defined JNI interface, existing submodule from matthewn4444. Many classic VNs run on NScripter.
2. **Godot second** — technically simple, just needs Maven dep + Activity. But verify there are actually games people want to play that ship as .pck files.
3. **Ren'Py last** — genuinely complex. Would need either a custom generic bootstrap (months of work) or per-game APK integration. Not practical for a launcher.

### If I were to start coding right now:

For **ONScripter**, I'd:
1. Add `matthewn4444/onscripter-engine-android` as a git submodule
2. Add its `src/main/java` to the Gradle source sets
3. Write `OnscripterActivity.kt` (~60 lines) that creates an `ONScripterView` with game path
4. Register it in AndroidManifest.xml
5. Update `NScripterEngine.kt` to launch the activity instead of showing "Coming Soon"
6. Verify build compiles

That's maybe 4 files total and the heaviest work is figuring out ONScripterView.Builder parameters.

For **Godot**, I'd:
1. Add `implementation("org.godotengine:godot:4.6.3.stable")` to build.gradle.kts
2. Remove `libgodot_android.so` from jniLibs (AAR provides it)
3. Also remove `libc++_shared_godot.so` (AAR provides this too)
4. Write the 20-line `RunestoneGodotActivity.kt`
5. Register it
6. Verify. But this adds (at minimum) a Maven download + the AAR extraction time to the build.

For **Ren'Py**, I'd skip it entirely — the effort isn't worth it for a generic launcher. Games that work on Ren'Py Android should be installed as their own APKs.
